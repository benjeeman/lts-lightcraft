# LTS browser byte bridge

The LTS fork retains the existing Rust engine, develop commands, browser canvas and native MCP server. Its `lts-byte-bridge.js` (version `lts-byte-bridge.v3`) adds two browser host functions and a version record to the existing `globalThis.lightcraft` object. Since v3 (fork batch R1) the bridge rides the LTS hook of this fork's WASM, `src/lts_view.rs`: it sends the hook's own `lts.*` ids and nothing else, so it needs a WASM built from this fork at R1 or later. The official 0.4.0 WASM and the fork's earlier packages have no hook: there an `lts.*` id reaches the editor's own command path, which does not know it.

- `importImage({name, bytes})`: PNG or JPEG bytes (a `Uint8Array`, or an array of integers 0 to 255) become a browser File and follow the same File-drop import service as a human drop; the drop is not a `lightcraft.command` call. Encoded inputs are bounded to 12 MiB. The 16-megapixel admission check occurs **after** browser decoding, so it is not a hard decoder-memory bound; a future header dimension precheck could reject oversized images before that allocation. The file gets a unique name, `lts-<random UUID>-<name>`, so repeated names cannot select an older image. The page imports a dropped file on a later frame, so the bridge then asks the hook for the library's photos of exactly that file name, `lts.library {fileName}`, every 100 ms for up to 15 s. The result is the hook's row for the photo (its id, its file name, its dimensions and its settings token `hash`, among the fields `catalog.query` gives) with `sourceName` and `transfer: "browser-file-drop"`.
- `exportImage({id, format, longEdge, metadata?, removeLocation?})`: the bytes come from `lts.export`, a pure output read: nothing is downloaded, selected or remembered (no last-export preference, no file, no Blob). PNG and JPEG are supported, long edge 16 to 4096, output at most 32 MiB. Every export passes an explicit metadata policy: `copyright` with the location removed unless the caller asks for `none` or `allExceptCamera` (owner decision OC-13); `all` (camera, lens and capture settings) is not offered. The bridge checks that the answer is the export asked for (the photo, the format, the MIME type and the policy the hook applied) and that its bytes are strict base64 of exactly `byteLength` bytes. The result has `mimeType`, `bytes` (a `Uint8Array`), the `metadata` and `removeLocation` applied, `export` (the hook's answer without its bytes: dimensions, settings token, catalog revision) and `transfer: "lts-export"`. Its `name` is `image-adjustments.png` or `image-adjustments.jpg`; the LTS host derives saved file names from the MIME type, so the name only travels in the result.
- `ltsByteBridge`: `{version: "lts-byte-bridge.v3", ltsView: "lightcraft.lts-view.v1", metadataPolicies, defaults}`. An adapter reads the hook version it may use from `ltsView` instead of probing with a command.

Both functions refuse unknown parameters, so that a misspelt key cannot fall back to a default. A refusal of the hook is thrown with its code and message (`Image adjustments refused lts.export: target_not_found: ...`), and an answer that is not the hook's typed envelope for the command sent is refused. The bridge itself rejects overlapping byte transfers. Rust WASM work still runs on the browser thread for an export; an in-flight export cannot be cancelled by a JavaScript timer.

This bridge is a host adapter around existing public browser services and the hook's reads. It does not create another MCP implementation, grant access to host filesystem paths, provide durable LTS publication, or synchronize a native catalog with the browser. The LTS host owns source/origin/session validation and serializes operations.

An isolated memory-store session (`?store=memory`) does not persist the browser catalog; its edits must be captured or exported before closing. In the LTS presentation a new library starts empty, without the demo photos, unless the page also has `demo`. Persistent web libraries continue to use upstream Web Locks and storage behavior. No native catalog is opened by the browser.

`xtask/src/web.rs` includes the bridge in the static bundles and compression. Bridges v1 and v2 could be overlaid on the official hash-verified v0.4.0 web release without rebuilding its WASM (a patched host with upstream WASM, not a newly compiled fork engine); v3 cannot, because it needs the hook. Such an overlay changes only the page's own copy (title, loading and load-failure text): the LTS presentation below needs a WASM built from this fork, packaged in a new versioned directory.

## LTS presentation (`?embedded`)

This takes effect with a WASM built from this fork, packaged in a new versioned directory, and a host that opens the engine with the `embedded` query parameter. The LTS lab does: it opens Image adjustments with `?store=memory&workers=1&embedded`. The exact name's presence decides; its value does not (`embedded`, `embedded=`, `embedded=1` all count; `embeddedx`, `x=embedded` and other spellings do not). The page's inline script and the WASM read it the same way, as `URLSearchParams` does, before anything loads or paints. It selects a presentation: it is not stored in `ui.json`, the catalog or preferences, grants no authority, and changes no storage, worker, export or metadata behavior. A new library starts without the demo photos unless the page also has `demo`.

In the LTS presentation:

- the page title, loading text and load-failure text say "LTS Image adjustments";
- menus, command catalogs (`engine.commands`, `ui.menu.list`, `ui.menu.tree`), the Keyboard Shortcuts list, the top bar and the About dialog show no community, website, Discord or upstream-support route;
- the five community commands (`app.discord`, `app.feedback`, `app.website`, `app.github`, `app.artcraft`) keep their ids but are refused with `Community navigation is unavailable in the LTS editor` on every path (menus, keys and the control channel), and the engine opens no external page at all: any other URL is refused with `External links are unavailable in the LTS editor`;
- `app.help` (F1) opens the local Keyboard Shortcuts ("Editing shortcuts"); About is "Editing engine information" with plain-text attribution, contributors as plain text and a Third-party notices tab; Quit is "Quit editor"; the second window is titled "LTS Image adjustments — Second Window"; the Info panel shows a photo's coordinates without the "Show on Map" button;
- the panic overlay says the editing session has ended and that changes kept only in the editor are not saved to LTS, without reload or upstream-support advice;
- since R1, `globalThis.lightcraft.command(id, params)` runs only the hook's commands. Every other id, whatever its parameters, is answered by the hook with a refusal and nothing runs: the engine's and the UI's commands, the engine's own queries (`library.state`, `catalog.query`, `develop.get`, `develop.controls`, `photo.inspect`, ...) and the page's `web.stats` alike. The refusal resolves the promise, it does not reject it: `{"resultVersion": "lightcraft.lts-view.v1", "command": <id>, "outcome": "not_applied", "code": "command_not_allowed", "message": ...}`. A caller must therefore read `resultVersion` and `outcome` of every answer; one that only awaits the call would take a refusal for a result.

The hook's commands (`POLICY` in `src/lts_view.rs`; every answer carries `resultVersion`, `command` and `outcome` `ok`, `applied` or `not_applied` with a registered `code`):

| Hook command | What it does | What it replaces |
|---|---|---|
| `lts.state {id?, settings?}` | the tokens: the photo's settings token `hash`, the catalog revision, the active photo, a human interaction in progress, the undo and redo heads; with `settings: true` also the complete settings that `hash` names | `library.state`, `develop.get` |
| `lts.library {offset?, limit?, fileName?}` | the library's photos as `catalog.query` lists them, each row with its `hash`; with `fileName`, the photos of exactly that file name | `catalog.query` |
| `lts.photo {id}` | `photo.inspect`, with the token of each step of the photo's history | `photo.inspect`, `history.list` |
| `lts.controls {id?}` | the control catalog: every develop control, the gates it acts behind (the states of the settings in which it changes nothing) and, for a photo, its values and the gates open for it | `develop.controls` |
| `lts.presets`, `lts.metadata {id}`, `lts.journal {limit?}` | `presets.list` with `profiles.menu` and `curve.presets`; `photo.allMetadata`; `journal.list` | the same queries |
| `lts.preview {id, longEdge, ...}` | the engine's render as a PNG without metadata, with its histogram and statistics, optionally a what-if or a mask's view | a preview made by exporting |
| `lts.export {id, format, longEdge, metadata?, removeLocation?}` | the encoded output under an explicit metadata policy, written nowhere | `app.export` |
| `lts.develop {id, values \| settings \| preset, expectHash?, ...}` | control values as `develop.set` sets them, complete settings (they require `expectHash`), a patch of sections or a preset, as one undo step | `develop.set`, `develop.sync`, `preset.apply` |
| `lts.crop {id, rect? and/or angle?, reset?, ...}` | the crop `crop.set` or `crop.reset` makes, whichever photo is active | `crop.set`, `crop.reset` |
| `lts.undo`, `lts.redo`, `lts.restoreSettings` | the top step, when it is that photo's alone; an earlier state the photo's history recorded (each requires `expectHash`) | `edit.undo`, `edit.redo`, `history.restore` |
| `lts.select {id, detail?}` | the declared selection: the photo selected and active, shown in the detail view with `detail: true` | `library.select`, `view.detail` |

Command ids, file formats, the XMP `lc:` namespace, storage names, the `lightcraft`/`lightcraftModule` globals, DOM ids and the bridge functions are unchanged. Export metadata (`Software`/`CreatorTool` "LightCraft") stays as truthful technical provenance. Without `embedded` the standalone presentation is upstream's: there `lightcraft.command` runs every id as before, and the `lts.*` ids reach the hook alike.

Validation: `node --test apps/lightcraft-web/lts-byte-bridge.test.mjs apps/lightcraft-web/lts-byte-bridge-r1.test.mjs apps/lightcraft-web/tests/embedded_presentation.mjs` (the bridge v3 against a page that refuses every id outside the hook, as the R1 WASM does, and the page's inline presentation script in a DOM fixture); Rust: `cargo test -p lightcraft-web --test lts_view --test lts_query_purity` (the hook, T-LI-02 to T-LI-28; T-LI-21 the refusal at the fork, T-LI-22 the reads that replace the engine's queries) and `--lib` (the `options` tests), `crates/ui-egui/tests/embedded_presentation_control.rs` and `crates/ui-egui/tests/embedded_presentation_ui.rs`. The page's inbox itself runs only in the WASM: the refusal of a raw engine id through `lightcraft.command` is checked end to end in a browser, on the package built from this fork. On 2026-10-08, with bridge v1 on the official WASM, an actual Chromium browser test imported a procedural 320×240 PNG, set exposure +1/contrast +12, cropped the center half and returned a 160×120 PNG. Independently decoded pixels matched the equivalent native MCP output exactly. This limited PNG test is not RAW fidelity or general performance qualification.
